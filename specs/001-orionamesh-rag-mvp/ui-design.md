# UI 设计规范：OrionaMesh 个人知识库 RAG MVP

> 文档职责：本文件是前端视觉语言、布局、交互、组件边界与客户端状态职责的唯一权威来源。
> 用户需求与验收以 `spec.md` 为准；API、错误码、SSE 和 DTO 以 `contracts/openapi.yaml` 为准；
> 实施架构与顺序以 `plan.md`、`tasks.md` 为准。本文件不重新定义服务端授权、状态机或业务规则。

## 1. 设计目标与原则

OrionaMesh 是面向个人研究与知识工作的 RAG 产品。界面应传达“可信、克制、精密”，而不是通用 AI
聊天工具的发光感或传统后台的拥挤感。视觉以编辑式知性为底，以建筑化的信息秩序组织高频操作。

- **证据优先**：回答、引用与资料状态必须可核验；没有可用证据时，明确呈现可信拒答，绝不以空白或普通回答掩盖。
- **高密度而可呼吸**：桌面首选布局在同屏呈现高价值信息，但依靠稳定网格、短间距和清晰层级避免压迫感。
- **信号式品牌**：品牌色只承担可解释的信号职责（主操作、可靠状态、引用、流式状态），不作为大面积装饰。
- **服务端为真相源**：前端只映射 DTO 中的 `status`、`allowed_actions`、`code`、`msg`、`trace_id` 与 SSE 事件；不得推导授权、状态机或删除语义。对本节明确列出的封闭错误集合，允许以固定安全文案改善可理解性；其余错误必须显示服务端 `msg`。
- **默认浅色、完整深色**：浅色是主体验；深色是“夜间编辑桌”，延续同一信息层次，不是简单反相。

## 2. 品牌与视觉令牌

### 2.1 色彩角色

| 角色        | 浅色                      | 深色                  | 使用边界                                                 |
| ----------- | ------------------------- | --------------------- | -------------------------------------------------------- |
| 页面基底    | `#F7F6F1` 暖白            | `#141918` 石墨        | 页面与低层容器，不用于强调操作                           |
| 表面        | `#FFFEFA` 纸白            | `#1B2220`             | 卡片、输入框、弹层                                       |
| 主文本      | `#202625` 石墨            | `#E6ECE8`             | 正文与标题                                               |
| 次文本/边界 | `#737B78` / `#DCE3DF`     | `#9BA7A1` / `#31403B` | 元数据、分隔与禁用态                                     |
| 可靠信号    | `#0C625D` 矿物青          | `#4CAE9C`             | 主按钮、选中、成功、已就绪、键盘焦点                     |
| 智能线索    | `#534CA5` 靛蓝            | `#AAA4ED`             | 引用序号、关联问题、流式光标；不得替代错误或成功颜色     |
| 警示/失败   | 可访问的琥珀/红色语义令牌 | 对应低饱和深色令牌    | 仅服务端已声明的告警、失败和危险操作；文本与图标同时表达 |

不得使用大面积渐变、持续发光、霓虹边框或以颜色单独区分状态。令牌必须定义为语义 CSS 变量并由
Tailwind 映射；组件不得硬编码产品色值。

### 2.2 排版、尺寸与动效

- 正文使用清晰的无衬线中文系统字体栈；展示级页面标题使用衬线中文系统字体栈（`Songti SC` 等回退），不依赖运行时外部字体请求。
- 标题强调编辑感，正文优先可读性；界面元数据使用小号、较宽字距的等宽或无衬线样式，不能小于 12px 的可读下限。
- 基础间距采用 4px 网格；高密度工作台常用 8/12/16/24px 间距。边框细而低对比，卡片阴影仅用于浮层与层级，不用于普通列表项。
- 动效只表示状态变化：抽屉、菜单和提示 160–220ms；流式回答只使用靛蓝插入光标；尊重 `prefers-reduced-motion`，不得依赖动效传达关键信息。

## 3. 布局与响应式

### 3.1 桌面工作台

目标视口为 1280px 及以上，1024px 仍必须完整可用。应用使用稳定的两层结构：

1. 左侧固定全局侧栏：顶部是品牌与折叠控制；中部为知识库管理、对话导航，以及仅在对话路由出现的会话历史列表；底部是稳定首字母头像菜单。历史列表直接分页展示当前用户全部会话，每行以所属知识库名称作次级标签；折叠不因折叠失去可访问名称。资料管理、知识库和个人资料页面隐藏会话历史，且侧栏不得自行猜测“当前知识库”。
2. 中央主工作区：页面标题、核心列表/对话和主操作；内容宽度优先服务阅读，不把聊天正文拉满整屏。会话历史绝不进入中央主内容区。对话页采用居中的单列阅读宽度，中央只呈现消息流、引用和固定输入区。默认不渲染无业务价值的右侧上下文栏；完整引用详情始终由按需抽屉呈现。

当前知识库选择位于对话主内容区顶部；它只在开始没有既有会话的新对话时承担必选范围。首次进入或 URL 未携带有效知识库时，左侧仍显示全局历史，正文选择器显示未选择状态，必须由用户明确选择，绝不回退到任意第一个知识库。选择控件须以分页、搜索或等价交互访问全部有效知识库。用户从该控件主动切换知识库且当前打开着会话时，必须先获得确认（将清空当前会话上下文），并重置当前会话和引用选择；点击任一历史会话则直接进入并以 URL 恢复其已绑定知识库，不使用此确认。历史列表按最近活动排序，支持全局分页，每行展示所属知识库名称；会话标题为空时显示“未命名对话”。不提供额外的侧栏筛选器或“新建对话”按钮。主内容区空态输入首条内容时自动创建会话并写入全局历史。对话正文顶栏重复显示已绑定知识库作为可见上下文，但不把选择器放入输入框。消息区独立滚动，输入区固定在工作区底部（圆角悬浮卡片、聚焦无边框），发送/取消为输入框内右下角小图标按钮，快捷键提示位于输入卡片内。发送后先展示用户消息与助手生成状态，终态后由服务端记录接管；新内容到达时在用户停留底部的情况下跟随，用户阅读旧消息时改为提供回到最新内容入口。会话与知识库选择必须由 URL 恢复，以支持刷新、后退前进和深链接。

在小于 1024px 的视口，左侧导航折叠为可访问的抽屉，抽屉保留导航与账户等价入口（个人资料、主题切换和退出登录）；用户位于对话路由时，同一左侧抽屉提供带知识库标签的全局会话历史。引用抽屉改为全高覆盖层。
移动端不是 MVP 的首要优化目标，但所有已交付操作必须可访问，不能仅以隐藏控件降级。

### 3.2 页面模式

| 页面       | 主界面                        | 关键体验                                                                 |
| ---------- | ----------------------------- | ------------------------------------------------------------------------ |
| 登录、注册 | 简洁居中的纸白认证表单        | 最少干扰；错误紧邻字段；安全提示不泄漏服务端细节                         |
| 知识库     | 高密度列表/卡片与创建入口     | 名称、描述和资料规模清晰；创建成功后进入名称明确的资料工作区；`delete_failed/20015` 只显示最小墓碑与重试删除 |
| 资料       | 列表优先、右上上传与详情抽屉  | 标题显示所属知识库；右上主操作打开上传面板，空列表提供等价操作；接受后立即出现明确非终态资料行并反馈资料数；DTO 驱动状态、阶段、失败原因与 `allowed_actions`；处理进度不得伪造为完成 |
| 会话       | 左侧工作区侧栏会话历史 + 中央标准 AI 对话流 | 会话历史仅在对话路由出现在左侧侧栏，默认列出当前用户全部会话（全局分页、知识库名称标签、操作收进扩展菜单），绝不进入正文；点击历史会话直接恢复其绑定知识库；正文为受控阅读宽度的单列消息流，用户右侧紧凑气泡、助手左侧无边框正文，引用紧随回答；知识库选择在正文顶部，仅在空态新建时必选且不默认猜测；输入区固定底部且聚焦无边框，发送按钮为输入框内图标 |
| 引用       | 紧凑证据卡 + 按需右侧抽屉     | 引用卡显示顺序、资料名/快照与定位摘要；点击查看合法 DTO 范围内的完整来源 |

## 4. 可信问答与引用交互

会话采用“专注对话界面”。助手回答紧邻紧凑证据卡，而非永远占用第三栏：

- 中央消息流采用单列阅读宽度；用户消息在右侧使用紧凑、低饱和气泡，助手回答在左侧使用无边框正文。不得将用户与助手都渲染为相同的边框卡片，也不得在正文重复会话列表。
- 助手长回答优先使用清晰的段落、标题、列表和代码排版；引用位于该回答下方，采用低干扰的紧凑证据条目，而非抢占正文的独立大卡片。
- 回答内以可访问的编号引用标记对应 `Citation`；同一答案下方按服务端 `rank` 顺序展示证据卡。
- 证据卡显示引用序号、资料名称或快照标识、定位摘要；点击或键盘激活打开 `CitationDrawer`。
- `source_type=live` 仅在接口提供合法当前来源 ID 时展示可用定位入口；`snapshot` 只展示保留快照，绝不构造原始资料访问入口。
- “未找到相关证据”、`failed/error`、`cancelled/cancelled` 必须是消息流中的独立、明确终态；不显示无依据的补全，也不把取消伪装为失败。
- SSE 进行中显示用户刚提交的问题、助手无边框正文末尾的靛蓝光标与简短生成提示；收到终态事件后移除光标、固定终态，并使焦点与屏幕阅读器公告不过度打断阅读。多行消息按原有换行展示。

## 5. 组件体系

Shadcn/UI 是基础组件来源和可维护代码所有权边界。遵循其可组合模式，并在 `src/components/ui/` 中维护
项目内副本与令牌映射；业务组件不得复制基础交互。

| 层级      | 组件                                                                                                       | 规则                                                                 |
| --------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 基础      | Button、Input、Label、Textarea、Select、Checkbox、Tooltip、Skeleton、Separator                             | 使用语义变体，统一焦点、禁用与错误态                                 |
| 容器/反馈 | Card、Dialog、AlertDialog、Sheet、DropdownMenu、Toast、Badge、EmptyState                                   | 危险删除必须用 `AlertDialog`；错误要保留 `trace_id` 的可复制诊断入口；创建、保存、重命名、删除和上传接受使用克制的短暂成功反馈 |
| 应用壳    | `AppShell`、`WorkspaceNav`、`ConversationSidebar`、`AccountMenu`、`ThemeToggle`                             | 全局壳只维护布局和导航本地状态；`ConversationSidebar` 组合在左侧 `WorkspaceNav`，仅在对话路由显示当前用户全局历史，不得在无关页面猜测业务真相或移入中央内容；默认不使用 `ContextRail` |
| 领域      | `DocumentStatus`、`TaskHistory`、`MessageThread`、`CitationCard`、`CitationDrawer`、`ConversationFeedback` | 接受冻结 DTO；不自行推断服务端状态或操作权限                         |

必须为空列表、初次加载、刷新加载、可恢复错误、权限不可见、可信无证据、SSE 失败/取消及删除确认提供
明确组件状态。`delete_failed/20015` 墓碑保持既有“最小且无名称/描述/子资源入口”限制，不得被通用卡片样式放大或泄露信息。

## 6. 前端状态与数据获取

### 6.1 职责划分

- **TanStack Query**：唯一的 REST 服务器状态缓存层。负责查询、分页、失效、资料非终态轮询、加载/错误状态和 mutation 后的精确失效。查询键按资源层级构造（例如 `knowledgeBases`、`documents`、`conversations`、`messages`、`citations`），不得把服务端实体副本放进 Zustand。
- **SSE Hook**：`useMessageStream` 负责一次发送与事件消费。每个事件仅更新当前流式草稿；终态后失效对应消息/引用查询，使服务端持久化结果重新成为界面真相。断开、错误或卸载必须关闭连接。
- **Zustand**：仅保存短生命周期、客户端 UI 状态：导航折叠、当前已打开的引用抽屉选择器（由 `messageId + rank` 组成，不是 Citation DTO 中不存在的 ID）、非敏感的临时筛选/视图偏好。不得保存 token、用户密码、Refresh Token、授权结论、资料/会话实体、任务状态或服务端错误码。
- **next-themes**：负责浅色/深色和系统偏好持久化；主题不进入业务状态仓库。
- **React Hook Form + Zod**：用于本地表单输入、可访问字段错误和提交前结构校验；服务端 `code/msg` 是最终业务反馈，前端校验不得替代服务端限制。

### 6.2 缓存与错误规则

- 资料仅在 DTO 表示非终态时轮询；轮询间隔、停止条件与失效由单一查询封装维护。
- mutation 默认不自动重试非幂等写请求；上传重放只使用已冻结的 `Idempotency-Key` 行为。
- 上传遇到可恢复的 `10001/401` 时，必须复用统一会话轮换并以原始 `Idempotency-Key` 重放一次；重放后仍失败才展示错误，且不要求用户重新选择文件。
- 资料列表的轮询不能只依赖当前筛选页中的项目：上传批次未收敛时必须持续失效对应知识库资料查询，直到该批次均为明确终态。
- 上传被接受后必须立即失效或更新当前知识库的资料列表，使已接受资料在处理期间可见；上传中的批次不得复用单一进度或接受反馈覆盖彼此。
- 当前会话切换、删除、404 或授权失效时必须同步关闭引用抽屉选择器；不得让旧 `messageId + rank` 进入新会话查询。
- 会话历史查询未带知识库筛选时是当前用户的全局分页缓存；点击历史会话后，必须同时更新 URL 中的会话与其绑定知识库，并失效或更新该全局查询。不得将全局分页 total 当作某一知识库的页数。
- 认证失效、429 与其他业务错误统一由 API 客户端解码后交给页面反馈组件；默认显示安全的 `msg` 和可复制 `trace_id`，不展示原始响应、令牌或堆栈。仅 `10001`、`20007`/HTTP 404 与 `10005`/HTTP 429 可映射为固定友好文案；映射不改变 `trace_id`、状态或重试信息，未匹配时必须回退服务端 `msg`。表单字段错误紧邻字段，写操作错误紧邻操作区域并提供适用重试；认证恢复、列表/详情加载和无效深链接必须提供完整错误状态、重试及返回安全入口。读取失败时不得将空数据状态作为替代呈现；会话详情加载中必须有明确加载态。
- 客户端本地状态在登出时清空；Query 缓存不得跨用户会话复用。

## 7. 可访问性与质量要求

- 正常文本与背景至少满足 WCAG AA 对比度；焦点环始终可见，键盘顺序与视觉顺序一致。
- 所有图标按钮有可访问名称；对话框、抽屉与下拉菜单具备焦点圈定、Escape 关闭与焦点回归。
- 状态同时通过文字、图标与颜色表达；加载骨架不代替可理解的终态消息。
- 流式回答、上传/处理状态和 toast 使用克制的 `aria-live`，只公告新增的必要状态，避免逐 token 朗读。
- 使用 Shadcn/Radix 原语时保留其键盘和 ARIA 行为；新增封装必须有组件测试覆盖关键键盘路径。长消息列表的自动跟随与“回到最新内容”入口必须不抢走键盘焦点、不干扰用户主动阅读旧消息。

## 8. 实施边界与验收

- 前端依赖为 `@tanstack/react-query`、`zustand`、`next-themes`、`react-hook-form`、`zod` 与 Shadcn/UI；新增依赖必须由 pnpm 根锁文件锁定。
- 先完成主题令牌、应用壳、Query Provider、UI store 与基础组件，才进入会话、SSE 与引用页面渲染。
- 新增视觉实现需要验证浅/深色切换、键盘焦点、引用抽屉、SSE 三类终态及现有资料删除墓碑不变量；并覆盖注册密码提示与确认密码、认证恢复失败、知识库创建跳转和重名、上传接受后即时资料行/筛选后终态/并发批次、资料详情抽屉、全局会话历史/跨知识库点击恢复/无默认知识库/错误/删除、首条消息即时呈现、消息换行与跟随、引用跨会话关闭和窄屏账户菜单。这些是 Vitest 单元/组件确定性前端行为测试；不保留 Playwright 或浏览器端 E2E，也不将 SC-001～SC-007 转化为自动化门禁。
- 本次允许为全局会话历史更新会话列表 DTO；其余冻结 API、数据模型、错误码、模型出口或服务端状态机不得改变。任何后续契约变化仍必须先更新各自的权威文档。
