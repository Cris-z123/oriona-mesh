# 研究记录：OrionaMesh 个人知识库 RAG MVP

## 决策 1：后端优先、前端后置

**决定**：先完成后端领域逻辑、数据库迁移、异步流水线及 REST/SSE 契约；仅在 A5 验证
门禁通过后开始前端渲染。

**理由**：资料状态、租户过滤、检索证据与 SSE 终态均为后端权威规则。先冻结可测试契约可
防止前端根据猜测实现状态机或权限逻辑。

**备选方案**：前后端并行开发；拒绝，因为当前项目无既有稳定接口，易导致契约漂移。

## 决策 2：任务状态以 PostgreSQL 为真相源

**决定**：`documents`、`document_tasks` 与 `document_task_attempts` 保存用户可见状态和审计
事实；Celery/Redis 只负责投递与执行。

**理由**：执行器状态可丢失或过期，不能用于恢复或展示。资料详情轮询和任务详情 API 只读
数据库状态；工作进程在阶段边界持久化状态、进度或失败。

**备选方案**：直接展示队列任务状态；拒绝，违背单一真相源原则且无法可靠处理重启。

## 决策 3：上传限制在接收前拒绝

**决定**：服务端在创建资料和任务前验证格式、单文件 50MB、单次 20 文件与当前用户对知识库
的归属；违反时返回统一错误且不创建半成品记录。

**理由**：限制是产品行为，提前拒绝不会污染异步队列或状态机。

**备选方案**：先入队后在 worker 检查；拒绝，因为用户获得延迟失败且会创建无意义任务。

## 决策 4：检索必须双路、证据不足必须拒答

**决定**：对当前用户和会话知识库，向量与关键词召回各取前 10 项；RRF 融合，重排器可选；
无完成资料或无相关证据时不生成知识库结论。

**理由**：双路检索改善召回鲁棒性，拒答确保 RAG 产品可信。可选能力失败时回退而非中断可用
路径。

**备选方案**：仅向量召回或允许自由发挥；均拒绝，分别降低召回覆盖和证据可信度。

## 决策 5：删除资料保留最小引用快照

**决定**：资料删除后不得参与新检索；历史 `message_citations` 保留当时的文件名、定位及内容
预览快照，但不能恢复或读取原始资料。

**理由**：同时满足“删除即不可再检索”和历史回答可审计。

**备选方案**：删除全部引用或保留可访问原始文件；前者破坏审计，后者违反删除语义。

## 决策 6：SSE 断开采用持久化取消终态

**决定**：用户消息先持久化；若 assistant 消息已创建而 SSE 客户端断开或生成取消，更新为
`cancelled` 并写入结束原因；不得保留未结束的 `streaming` 状态。

**理由**：统一终态便于历史展示、诊断与测试，符合无半成品可见状态原则。

**备选方案**：删除未完成 assistant 消息；拒绝，因为会丢失用户问题对应的处理事实。

## 决策 7：统一响应、认证与全链路追踪

**决定**：除 SSE 外，所有 API 使用 `{ code, data, msg, trace_id }` JSON 信封；SSE 的每个
事件 `data` 也使用该信封。成功码固定为 `0`；业务错误码与 HTTP 状态码分别表达业务分类和
传输语义。JWT 通过 Bearer 请求头传递，Access Token 有效期为 2 小时，Refresh Token 有效期为
7 天。中间件为每个请求生成或接收 `trace_id` 并注入 structlog 上下文。

**理由**：前端可稳定以 `code` 决策，`trace_id` 可关联用户反馈与结构化日志。JSON 信封要求
删除操作返回 `200` 而不是无响应体的 `204`。

**安全规则**：日志过滤 `password`、`token`、`secret_key` 及其嵌套变体；响应不得回显密码或
刷新令牌以外的敏感原始数据。错误码至少包括：`10001/401` Token 过期、`10002/403` 无权访问、
`10003/400` 参数校验失败、`10004/401` 登录凭证无效、`10005/429 RATE_LIMIT_EXCEEDED` 请求过于频繁、
`10006/401 INVALID_REFRESH_TOKEN` 刷新令牌失效、
`20001` 资料解析失败与 `20010 EMPTY_DOCUMENT` 空资料（均由详情 HTTP `200` 持久化返回）、
`20002/404` 知识库未找到、`20003/400 FILE_TOO_LARGE` 文件超限、
`20004/400 TOO_MANY_FILES` 批量数量超限、`20005/409 KNOWLEDGE_BASE_NOT_READY` 无已完成资料、
`20006/409 EMAIL_ALREADY_EXISTS` 邮箱已注册、`20007/404` 资源不存在、`20008/409` 资源冲突、
`20009/400 UNSUPPORTED_FILE_TYPE` 不支持的资料格式，
以及 `50000/500` 内部错误。

**备选方案**：沿用 HTTP 状态码和各接口自定义错误体；拒绝，因为会提高前端判断分支和跨服务
排障成本。

## 决策 8：配置驱动的模型适配与弹性策略

**决定**：使用 LangChain 适配器封装可通过环境配置选择的模型供应商、端点、密钥和四类模型；
不在业务代码中写死供应商。Embedding 默认 `text-embedding-3-small`（1536 维），Query Rewrite 和
Generation 模型必须显式配置；Reranker 模型为空时禁用重排并直接使用 RRF。变更 embedding 维度时
必须配套迁移与重建。四类模型名、超时和最大重试次数使用 Quickstart 固定的 `MODEL_GATEWAY_*`
变量名，应用启动时校验必填项和取值范围。

**调用策略**：Embedding 超时 30 秒，指数退避重试 2 次，最终以 `20012` 将当前资料和任务收敛为失败；
Query Rewrite 超时 10 秒、重试 1 次，最终使用原问题；Reranker 超时 10 秒、重试 1 次，最终
跳过重排直接使用 RRF；生成首 token 超时 15 秒、总时长 120 秒、重试 1 次，最终失败或连接
断开把 assistant 消息收敛为 `cancelled`，不生成无证据回答。

**理由**：供应商可替换而业务行为稳定；每个失败分支均保留明确、可信、可诊断的结果。

## 决策 9：可复现工程工具链与发布门禁

**决定**：Python 依赖使用 uv 管理，提交 `uv.lock`，CI 使用 `uv lock --check` 与 `uv sync --locked`；
前端使用 pnpm，仓库只提交根目录 `pnpm-lock.yaml`，CI 使用 `pnpm install --frozen-lockfile`。后端执行 Ruff
format/check、Pyright、pytest 与 OpenAPI 校验；前端执行 ESLint、Prettier check、TypeScript
类型检查、Vitest 和 Playwright。Docker Compose 提供本地全栈依赖；GitHub Actions 执行质量门禁
及受保护分支上的镜像构建/发布。

**理由**：锁定依赖和自动化质量门禁使开发、CI 与部署使用同一输入，避免环境漂移。

## 决策 10：请求限流采用后端内部 Redis 分级策略

**决定**：限流作为 `backend/app/infrastructure/rate_limit/` 内部模块实现，不新增独立服务。
Redis 保存跨 API 实例共享的临时计数，使用原子滑动窗口或行为等价算法；限流计数不是业务
状态，不写入 PostgreSQL。注册和登录同时按来源 IP 与规范化邮箱限制；刷新请求没有邮箱字段，
因此按来源 IP 与 refresh token 的 HMAC 指纹限制。账号、token 指纹与用户键必须经过带服务端
秘密的不可逆摘要处理；上传、问答和普通认证接口按当前用户限制，原始 refresh token 不得进入
Redis 键、日志或指标标签。

默认阈值为：认证每 IP 20 次/5 分钟且每账号 5 次/5 分钟；上传每用户 10 次/10 分钟；问答
每用户 20 次/分钟；其他认证接口每用户 120 次/分钟。阈值、窗口和键前缀均可配置。任一适用
策略超限时返回 `10005/429 RATE_LIMIT_EXCEEDED`、固定提示“请求过于频繁，请稍后再试”、
`Retry-After` 和统一响应信封，且必须在任何资料、消息、任务或会话写入前拒绝。

**可靠性决定**：Redis 不可用时，所有状态变更端点 fail-closed，返回 `50001/503`，避免保护
机制失效或在未计数时产生业务副作用；只有只读 GET 接口可按配置 fail-open，并记录不含主体
原值和请求内容的降级元数据。
`503` 表达临时不可用，并使用专用业务码 `50001 RATE_LIMIT_PROTECTION_UNAVAILABLE`，不与普通
`50000/500` 内部错误混用，也不伪装成用户触发的限流。

**理由**：分级策略匹配爆破防护、存储/解析资源和模型调用成本；内部模块复用现有 Redis，
在 MVP 中比独立网关服务更小，同时通过原子计数保持多实例一致。

**备选方案**：所有接口统一阈值；拒绝，因为资源成本差异大。进程内计数；拒绝，因为多实例
不一致且重启丢失。独立限流服务；延期，因为当前规模不值得增加部署单元。

## 决策 11：模型调用统一经过后端内部出口网关

**决定**：在 `backend/app/infrastructure/model_gateway/` 定义网关协议、调用上下文、脱敏器、
弹性策略、审计器和供应商适配层。Embedding、Query Rewrite、Reranker 与回答生成只能依赖该
协议；只有 `model_gateway/providers/` 可以导入供应商 SDK、LangChain 供应商集成或创建外部
模型 HTTP 客户端。网关与 FastAPI/Celery 位于同一代码库和部署镜像，不公开新的网络端点。

调用顺序固定为：最小化输入 → 敏感数据检测/脱敏 → 供应商与模型路由 → 发送边界凭证注入
→ 超时/重试 → 既定降级 → 白名单元数据审计。供应商配置保持环境可调，不在业务代码写死。

**理由**：一个不可绕过的代码级出口边界能够统一安全、弹性和审计行为，同时避免 MVP 引入
独立代理服务的网络跳数、部署和可用性负担。架构测试可以稳定禁止旁路依赖。

**备选方案**：独立网络网关；延期到需要跨服务复用或集中网络策略时。每个适配器自行处理；
拒绝，因为脱敏、重试和日志规则会漂移且难以证明不存在旁路。

## 决策 12：外部模型数据最小化、统一脱敏与 fail-closed

**决定**：网关只允许发送当前调用所需的最小内容。禁止外发密码、访问/刷新令牌、API 密钥、
Authorization/Cookie 等请求头、内部绝对存储路径及可直接识别租户的内部标识。邮箱、电话、
身份证件号等个人标识在不影响任务语义时替换为当前调用内稳定的不可逆占位符；不得建立可逆
映射或把原值放入任务 payload、异常和日志。

脱敏器异常，或发现禁止外发数据却无法可靠处理时，网关 fail-closed：不得创建外部网络请求。
Query Rewrite 回退原问题，Reranker 回退 RRF，Embedding 按既定重试后以 `20012` 使任务失败，生成按既定
重试后将 assistant 消息收敛为 `cancelled`。安全拒绝使用内部错误分类，不向用户暴露原文、
供应商响应或具体敏感字段。

**理由**：默认拒绝才能保证出口网关在规则或组件异常时仍是安全边界；最小化数据减少供应商
侧暴露面，又不持久化额外敏感映射。

**备选方案**：脱敏失败继续发送；拒绝，因为会让安全规则在最需要时失效。仅过滤固定字段名；
拒绝，因为文档内容和提示词中也可能包含敏感数据。

## 决策 13：模型调用日志采用严格字段白名单

**决定**：模型调用日志只允许 `trace_id`、调用 ID、经不可逆处理的用户/租户标识、调用类型、
供应商、模型、开始/结束时间、耗时、状态、错误分类、重试次数、输入/输出 token 数量和载荷
字节数。禁止请求/响应正文、提示词、用户问题、资料片段、文件名、请求头、凭证和可逆摘要；
脱敏后的正文同样禁止记录。供应商异常在写日志前转换为稳定错误分类。

**理由**：该白名单足够支持链路追踪、容量/成本统计和故障诊断，同时消除正文因日志采集、
索引或转储造成的第二份数据副本。

**备选方案**：记录脱敏摘要；拒绝，因为摘要仍可能包含业务内容且会扩大脱敏规则验证范围。
只记录极少字段；拒绝，因为无法定位供应商、重试和容量问题。

## 决策 14：对话绑定与级联删除采用严格知识库边界

**决定**：MVP 的 `conversations.knowledge_base_id` 必填并使用 `ON DELETE CASCADE`。删除知识库时
级联删除其对话、消息和引用；删除资料时不删除历史引用行，只将可选源外键置空并使用引用快照。
`messages` 冗余保存 `user_id`；`message_citations` 冗余保存 `user_id` 与 `knowledge_base_id`，并
建立租户前缀索引。引用读取必须先校验当前用户与对话归属。

**理由**：MVP 只提供知识库问答，不存在合法的无知识库对话。级联语义消除孤立状态；租户冗余
键让高频消息和引用查询具有明确、可测试的隔离边界，同时资料删除仍保留可审计证据快照。

**备选方案**：知识库删除后保留纯对话；拒绝，因为与 MVP 范围冲突且会让历史回答失去所属
安全边界。只通过外键链推导用户；拒绝，因为弱化了宪章要求的防御性隔离。

## 决策 15：列表分页按资源访问模式分为页码与游标

**决定**：知识库、资料、任务、对话和引用列表使用 `page`（默认 1，最小 1）与 `page_size`
（默认 20，最大 100），响应返回 `items`、`page`、`page_size`、`total`。消息历史按稳定的
`created_at + id` 顺序使用 `before` 消息 UUID 和 `limit`（默认 50，最大 100），响应返回
`items`、`has_more` 和 `next_before`。资料列表额外允许 `status` 枚举过滤。

**理由**：管理型列表需要总数和可跳页；持续增长的消息时间线使用游标可避免插入新消息导致
重复或跳项。显式上限防止无界响应占用数据库和 API 资源。

## 决策 16：资料与任务响应使用可直接实现的完整 DTO

**决定**：Document 响应统一使用 `version`、`current_task_type`、重试/片段计数、处理时间、
安全错误摘要与服务端计算的 `allowed_actions`；DocumentTask 响应包含任务类型、资料版本、重试
上限、进度、各阶段时间和结构化尝试记录。状态枚举分别遵循资料与任务状态机，不复用通用词表。

**理由**：完整 DTO 让轮询、故障展示和契约测试无需猜测字段映射；`allowed_actions` 避免前端把
Phase 2 的重处理能力误认为 MVP 可用。

## 决策 17：刷新令牌与上传类型使用专用错误码

**决定**：登录凭证错误使用 `10004/401`；刷新令牌无效、过期、撤销或重放使用
`10006/401 INVALID_REFRESH_TOKEN`，提示“登录状态已失效，请重新登录”。不支持的上传格式使用
`20009/400 UNSUPPORTED_FILE_TYPE`，提示“仅支持 PDF、DOCX、MD 和 TXT 文件”。文件大小与数量
继续分别使用 `20003`、`20004`。

**理由**：调用方可以依据稳定业务码采取重新登录或修正文件的动作，不依赖错误文本，也不会
把登录密码错误与刷新会话失效混为一谈。

## 决策 18：SSE 使用有类型事件和统一数据信封

**决定**：OpenAPI 以 `SseEvent` 的 `oneOf` 和 `event` discriminator 描述解码后的
`message_start`、`retrieval_done`、`delta`、`message_end`、`error` 对象；每个 SSE 帧的 `data`
都是 `{code,data,msg,trace_id}` JSON。成功事件的 payload 分别使用专用 schema，错误事件使用
错误信封。断连后已创建的助手消息固定持久化为 `cancelled`。

**理由**：事件名、payload 和信封均可由契约测试验证，前端可以生成判别联合类型；固定取消
终态满足“无半成品可见状态”，避免实现自行选择删除或保留。

## 决策 19：四类资料使用锁定解析器与统一安全边界

**决定**：PDF 使用 PyMuPDF 按页提取文本，MVP 不包含 OCR；DOCX 使用 python-docx 提取段落、
标题和表格；Markdown 使用 markdown-it-py 解析结构；TXT 使用 charset-normalizer 探测编码，
随后统一规范化为 UTF-8 文本。依赖版本由 `uv.lock` 固定，解析结果记录解析器名称和版本。

所有解析器使用同一安全包装层：不执行宏、脚本、外部链接或嵌入对象，拒绝路径穿越与符号链接
逃逸，限制解析时长、归档条目数量和解压后总大小。扫描 PDF 或标准化后无文字的资料以
`20010 EMPTY_DOCUMENT` 持久化失败，不进入 chunk/embed；损坏或不可解析资料使用 `20001`。

**理由**：明确解析器消除实现选择漂移；统一安全包装能够覆盖 DOCX 压缩炸弹和恶意路径等跨格式
风险。空文本与文件损坏是不同的可诊断结果，不应复用同一提示。

## 决策 20：异步处理错误通过资源状态返回

**决定**：上传接口只对同步校验失败返回 `4xx`，接受成功返回 `202`。解析等异步阶段失败后，
客户端轮询资料或任务详情并得到 HTTP `200`；响应中的 `status=failed`、`error_code` 和
`error_message` 表达持久化失败事实。`20001`、`20010`～`20014` 是业务错误码，不对应异步轮询的 HTTP 400。

**理由**：异步错误发生在上传响应完成之后，无法追溯修改原始 HTTP 响应；把错误写入数据库
符合单一真相源原则，也使刷新页面后的用户仍能看到一致结果。

## 决策 21：重复内容与请求重放采用不同语义

**决定**：内容哈希只用于完整性与诊断，不设置跨资料唯一约束；用户重复上传相同内容时创建
独立 Document。批量上传支持可选 `Idempotency-Key` 请求头，同一用户、同一知识库和同一键在
保留期内返回首次 `202` 结果，不重复创建文件对象、资料或任务。该记录由数据库唯一约束保证，
不得依赖 Celery 或 Redis 作为真相源。

**理由**：用户可能有意保留同内容但不同名称/上下文的资料，而网络重试不应制造意外副本；
分离两种语义可以同时满足产品意图和接口可靠性。

## 决策 22：处理并发名额由数据库事务管理

**决定**：单用户同时处于 `processing` 的资料默认最多 3 个，配置可覆盖。worker 在数据库事务
中原子获取与资料/任务绑定的名额；未获名额的任务保持 `pending`/`queued`。资料或任务进入
completed、failed、cancelled、deleting/deleted 时释放名额。恢复扫描器发现 lease 过期且任务仍为
`running` 时，必须在同一事务中锁定任务和 lease、把活动 attempt 关闭为 `failed`、释放 lease；
尚有重试预算则递增重试并把任务恢复为 `queued`，否则按已知阶段错误码或无稳定根因时的 `20014`
使任务与资料失败。同一任务不得同时存在两个活动 attempt。

**理由**：数据库是任务状态唯一真相源，事务名额能跨多个 worker 保持准确；仅用 Celery 并发
或 Redis 锁会在消息丢失、过期或重启时产生不可解释的占用状态。

## 决策 23：MVP 默认使用本地持久卷

**决定**：MVP 的原始资料、临时对象和解析中间产物默认写入容器内 `/data/orionamesh`，部署时
必须挂载命名卷或明确的持久化目录。数据库只保存相对对象键，存储适配器负责规范化、原子提交、
清理和防止路径逃逸。对象存储适配器保持接口扩展点，但不属于 MVP 默认交付依赖。

**理由**：本地持久卷使单机 MVP 可部署且不引入对象存储运维成本；相对对象键保留后续迁移能力，
并避免把开发机或宿主机绝对路径固化到领域数据。

## 决策 24：SSE OpenAPI 描述线格式与解码对象分层

**决定**：`text/event-stream` 的媒体 schema 使用 `type: string` 表达真实线格式；通过
`x-sse-event-schema` 指向 `SseEvent` 判别联合，描述客户端解码后的事件对象。契约测试同时断言
原始帧的 `event:`/`data:` 编码和解码后 `oneOf`/discriminator 结构。

**理由**：SSE 在线上传输的是文本帧而非单个 JSON 文档；把媒体 schema 直接声明为对象会误导
代码生成器。扩展字段同时保留可验证、可生成的事件类型信息。

## 决策 25：片段采用 embed 直写、finalize 逻辑发布

**决定**：沿用设计文档事务边界，`embed` 按批次和唯一键幂等写入正式 `chunks`，`finalize` 不再
搬运数据，只校验当前资料版本的草稿数、正式片段数、版本和任务结果，成功后原子翻转
`documents.status=completed` 并更新 `chunk_count`。finalize 前的行是物理存在但逻辑未发布的数据。

所有 `chunks` 读取收口到统一 `ChunkRepository`。检索方法固定连接 `documents` 并过滤当前用户、
知识库、完成状态和当前版本；流水线方法仅允许按用户、知识库、资料和精确版本计数或校验。
架构测试禁止路由、服务和 worker 直接读取 `chunks`。

**理由**：该方案保持短事务和 embed 重试幂等，不引入第二套发布表；统一仓储将正确性约束从
调用者约定提升为可测试的单一入口，确保未 finalize 数据不会被业务读取。

## 决策 26：批量上传同步校验采用整批原子语义

**决定**：接收文件后先完成整批格式、单文件大小和数量预校验；任一文件失败时返回对应 `400`
并保证整批没有资料、任务、幂等结果或文件对象。全部通过后生成内部 `upload_batch_id`，把临时对象
写到由批次和资料 ID 可推导的键，再在一个数据库事务中创建全部 `pending` 资料、不可执行的
`pending` 初始任务和可选幂等结果。数据库事务失败时删除全部临时对象。全部对象转正后，以一个
事务把整批资料、任务和幂等响应快照切换为 `queued`，再投递任务；任一转正失败则清理全部对象，
并在补偿事务中将三者收敛为 `failed/20011`，不得投递 parse，仍以 `202` 返回持久化失败资料。
恢复扫描器对超时 `pending` 上传批次执行幂等协调；批内每份资料已有正式对象或仍有完整临时对象
时完成剩余转正，否则整批补偿失败。只有完成转正并切换为 `queued` 的任务才能执行。
异步解析失败仍按每份资料独立收敛，不回滚同批其他已接受资料。

**理由**：全有或全无消除客户端对部分成功响应的猜测；批次 UUID 是资料内部协调字段，不引入
新的批次状态实体或服务，并关闭“数据库已提交但文件尚未转正时任务被扫描执行”的竞态窗口。

## 决策 27：异步处理失败使用最小稳定分类

**决定**：保留 `20001 DOCUMENT_PARSE_FAILED`、`20010 EMPTY_DOCUMENT`，新增
`20011 DOCUMENT_STORAGE_FAILED`、`20012 DOCUMENT_EMBEDDING_FAILED`、
`20013 DOCUMENT_FINALIZE_FAILED`、`20014 DOCUMENT_RETRY_EXHAUSTED`。已知阶段必须使用对应错误码；
只有恢复扫描器无法取得稳定根因时才使用 `20014`，未知内部故障使用 `50000`。这些错误通过资料
和任务详情的 HTTP `200` 持久化返回。

**理由**：六类错误足以支持用户理解和工程排障，同时避免为每个供应商或解析器异常建立错误码。

## 决策 28：处理名额归属于资料流水线

**决定**：资料首次进入 `processing` 时获取一个数据库名额，跨 parse、chunk、embed、finalize
持续持有；`task_id` 仅更新为当前阶段归属。资料终态、删除或失联恢复时释放。阶段切换不得释放
并重新获取。

**理由**：资料级名额与“同时 processing 的资料数”产品规则一致，避免阶段间重复竞争与饥饿。

## 决策 29：幂等记录清理由现有维护扫描承担

**决定**：Celery Beat 的任务恢复/维护扫描器在每轮扫描中按小批量删除已过期
`document_upload_requests`；不新增服务、队列或独立状态机。删除以 `expires_at` 为边界并记录数量
指标，不记录幂等键或请求指纹原值。

**理由**：这是低频数据库维护，复用现有定时入口即可满足 24 小时保留契约和数据增长控制。

## 决策 30：引用接口使用单一 DTO

**决定**：引用详情与 SSE `retrieval_done` 复用同一 `Citation` 字段语义：`rank`、`score`、可空的
`chunk_id/document_id`、`document_version`、`filename`、`file_type`、可空的 `page/section`、
`content` 预览和 `source_type=live|snapshot`。来源仍可访问时从活表返回 `live`；资料删除或来源不可
访问时，两个 ID 为空并从保存快照返回 `snapshot`。详情列表按 `rank` 升序并使用标准分页字段。

**理由**：一个 DTO 同时覆盖当前来源和历史快照，避免后端、SSE 与来源抽屉维护三套字段映射。

## 决策 31：资料删除使用专用清理任务、有界等待与 fencing

**决定**：DELETE 资料事务先标记 `deleting`、取消未开始任务，并幂等创建 `delete_cleanup`。
旧版本 `cleanup` 仍只清理非当前版本，不承担资料删除。若不存在运行 attempt，事务释放处理名额并
激活删除清理；若存在运行 attempt，则删除事务锁定 lease 并以当时的 `expires_at` 冻结等待上限
（默认最长 300 秒），资料进入 deleting 后心跳不得再续租。若 running attempt 没有活动 lease，
则立即按失联接管。
worker 每次写解析结果、草稿、正式 chunks、checkpoint 或阶段结果时，必须把 `attempt_id` 作为
fencing token，并在同一事务校验 attempt/task 为 `running`、版本一致且资料未进入
`deleting/deleted`。条件不满足时禁止写入并取消执行。worker 失联时，孤儿任务扫描器在 lease
超时后事务性关闭 attempt/task、释放名额并激活 `delete_cleanup`。清理完成后保留 `deleted` 墓碑
和历史引用快照。

**理由**：等待 worker 自觉停止没有终止保证；只发送 Celery revoke 也无法阻止已经运行或网络
分区中的进程写入。租约给出确定的等待上限，数据库 fencing 把“停止写入”变成原子前置条件，
专用任务同时避免违反宪章中 cleanup 只能清理旧版本的约束。

## 决策 32：Reranker 在 MVP 中是可选适配器

**决定**：MVP 实现统一网关后的可选 Reranker 适配器和 RRF 回退，但默认部署不要求配置或启用
Reranker；Phase 2 才把默认启用、模型选择和质量调优纳入交付。未配置不影响就绪状态。

**理由**：保留已设计的出口安全边界和扩展点，同时不把可选质量增强变成 MVP 部署依赖。

## 决策 33：SC-001～SC-007 仅作为产品成功指标

**决定**：SC-001～SC-007 中的性能、覆盖率和用户比例仅用于发布后的产品成功度观察与独立产品
验收，不建立固定评测集、比例断言、性能阈值 CI 任务、阶段门禁或发布阻断条件。其底层确定性行为
仍依据 FR 与用户故事进行单元、集成、契约或端到端示例测试，例如有证据时保存 Citation、无证据
时可信拒答、跨用户访问拒绝和引用可打开。SC-008 仍是自动化出口安全门禁。

**理由**：将产品结果指标与实现正确性门禁分离，避免不稳定的数据集、运行环境和用户行为阻塞
MVP，同时不降低租户隔离、可信回答、引用和安全出口等不可协商行为的验证强度。

## 决策 34：流水线阶段切换由数据库事务统一编排

**决定**：所有阶段通过统一 `DocumentPipelineOrchestrator` 完成切换。事务锁定 attempt、task、
document 与 processing lease；验证 fencing 条件后完成当前 attempt/task、按阶段幂等键创建或激活
下一任务、更新 `documents.current_task_type` 和 `lease.task_id`，再提交。Celery 投递仅发生在提交
之后；投递失败由对数据库 `queued` 任务的恢复扫描重投。`finalize` 在同一事务翻转资料完成状态并
释放名额，后续旧版本 cleanup 不影响发布状态。

**理由**：把“当前成功”和“下一阶段可执行”拆成多个事务会产生既成功又无后继、重复后继或 lease
仍指向旧任务的空窗。统一事务和阶段幂等键用最小机制消除这些不一致。

**备选方案**：Celery chain/chord 直接串联；拒绝，因为 Celery 不是状态真相源且投递状态不可替代
数据库恢复。

## 决策 35：上传 pending 采用明确超时与幂等接管

**决定**：上传文件转正协调默认超时 300 秒，由 `DOCUMENT_UPLOAD_PENDING_TIMEOUT_SECONDS` 配置。
API 按 `upload_batch_id` 对 documents 使用 `SELECT ... FOR UPDATE SKIP LOCKED`，在持有短事务行锁
时完成同卷原子重命名并更新批次活动时间；扫描器获取不到锁时跳过，只接管锁定后复查仍超时的
pending 批次，进程崩溃后行锁自动释放。同一
幂等键命中已收敛记录时返回首次结果；命中未超时 coordinating 记录时返回 `20008/409` 且无副
作用；命中超时记录时，重放请求可调用与扫描器相同的幂等协调函数接管。

**理由**：没有超时定义就无法区分活跃上传与进程崩溃；没有 coordinating 重放语义则并发网络
重试可能重复创建资源或得到不可预测结果。

**备选方案**：无限等待原请求或为上传另建独立协调服务；前者会挂起，后者超出 MVP 所需复杂度。

## 决策 36：知识库删除先编排清理再物理级联

**决定**：知识库先进入内部 `deleting` 状态，并对其资料复用资料删除编排。从事务提交开始知识库、
资料、对话入口和检索均隐藏。所有资料为 `deleted` 且无活动 attempt 后，由现有维护扫描器物理删除
知识库并级联对话、消息与引用；空知识库可同步删除。

**理由**：立即数据库级联会先删掉 worker 的状态真相和外键记录，却不会删除本地卷对象，也无法
阻止运行 worker 继续落数据。两阶段编排保留恢复所需事实，同时不新增独立服务。

**备选方案**：数据库立即级联后异步按路径猜测清理；拒绝，因为清理不可审计且易产生孤儿文件。

## 决策 37：登出撤销指定持久化会话

**决定**：`DELETE /auth/sessions` 需要 Bearer Access Token 和包含 `refresh_token` 的请求体。服务端
对刷新令牌做哈希，验证其会话属于当前认证用户后写入 `auth_sessions.revoked_at`；重复撤销保持幂等。
无法匹配任何会话或属于其他用户的刷新令牌返回 `10006/401`；已属于当前用户且已撤销或过期的
会话再次删除仍返回成功，以保持 DELETE 幂等。Redis 可缓存撤销结果，但不得
使用黑名单或直接删除作为唯一真相源。

**理由**：仅凭 Access Token 无法唯一识别需要撤销的刷新会话；持久化撤销与刷新轮换使用同一真相
源，避免 Redis 丢失后会话重新有效。

**备选方案**：Access Token 内嵌 session ID 且不提交 refresh token；可在后续演进，但当前契约已
明确由刷新令牌建立和轮换会话，增加 JWT claim 不是必要条件。
